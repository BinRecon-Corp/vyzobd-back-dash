# Storefront API Root Cause Analysis

Based on the audit of the application's routing and server configuration, there are two primary root causes for the issues described:

## 1. Unhandled Promise Rejections (Express 4)
The backend uses Express 4 (`^4.21.2`), which does not natively handle rejected promises in `async` route handlers. When an API route like `/api/storefront/v1/banners` is called, it executes the `getBanners` controller function. This function performs an asynchronous database query (`await storefrontContentService.getActiveBanners()`). If the database connection fails (e.g., `DATABASE_URL` is missing or the DB server is down), the promise rejects. Because there is no `try/catch` block and no `express-async-errors` middleware installed, the error is never passed to the Express `errorHandler`. This causes the request to hang and eventually drop (resulting in `* Empty reply from server` in curl), which appears to the frontend as the API being "non-functional".

## 2. Missing API 404 Catch-All (HTML Fallback)
The user reported that some API URLs return frontend HTML instead of JSON. This occurs because the application serves both the API and the React SPA on the same port. In `server.ts`, the frontend wildcard fallback (`app.get('*')` or `vite.middlewares`) is registered at the very end of the middleware chain.
If the frontend requests an API route with a slight typo (e.g., `/api/storefront/v1/banner` instead of `/banners`), or uses an unsupported HTTP method (e.g., `POST` instead of `GET`), Express will not match any API route. It bypasses the `errorHandler` (since no error occurred) and falls through to the wildcard SPA handler. The server then responds with `200 OK` and sends the React `index.html` file. The frontend attempts to parse this HTML as JSON, resulting in a `SyntaxError`.
